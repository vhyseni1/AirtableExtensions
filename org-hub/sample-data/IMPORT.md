# Sample data — import guide

Four CSVs that together describe one fictional 150-position organisation
(**Aurora Health Group**, 24 supervisory organisations, 4 management layers,
9 vacant positions) **and a restructuring of it**. They are generated by
`generate.py` and are internally consistent: every manager reference resolves,
every person sits in a supervisory org that exists, each org's headcount rollup
equals the FTE of its direct members, and the deck's current headcount
reconciles with the people table org by org.

| File | Rows | Becomes |
| --- | --- | --- |
| `Employees & Positions.csv` | 150 | the people table — one row per **position**, filled or vacant |
| `Supervisory Organizations.csv` | 24 | the supervisory-org table — one row per org unit |
| `Org Design Data.csv` | 185 | the flat table behind the stacked deck — one row per (slide, level, org, position, side) |
| `Org Design Notes.csv` | 9 | per-slide subtitle and commentary |
| `Programme Milestones.csv` | 24 | the PMO delivery plan |
| `Employee Conversations.csv` | 51 | the HR conversation tracker |

The first two feed the hierarchy views (position view, org trees, dashboard);
the last two feed the two stacked deck views. They are different shapes on
purpose — see the README.

Nothing here is real. Names, emails (`@aurorahealth.example`) and IDs are
synthetic.

## Import order

Import **Supervisory Organizations first**, then Employees & Positions — the
people table links into it. The two org-design tables are standalone and can be
imported in any order (they carry no link fields at all).

### 1. Supervisory Organizations

1. In your base: **Add a table → Import data → CSV file**, choose
   `Supervisory Organizations.csv`, name the table **`Supervisory Organizations`**.
2. Set the primary field to **`Supervisory Organization`**.
3. Convert these fields after import:

   | Field | Type | Notes |
   | --- | --- | --- |
   | `Parent Supervisory Organization` | **Link to Supervisory Organizations** | self-link; Airtable matches on the primary field |
   | `SO Status` | Single select | `No Changes SO`, `New SO - Draft`, `New SO`, `Updated SO`, `Decommissioned SO` |
   | `Scoping` | Single select | `In Scope`, `Out of Scope` |
   | `Org Level` | Number (integer) | |
   | `[C] SupOrgAssignement % Rollup (from Employees & Positions / FUTURE)` | Number (1 decimal) | in the real base this is a rollup; here it is a plain number |

   The root row (`Executive Office …`) has an empty parent — that's correct,
   it is the top of the tree.

### 2. Employees & Positions

1. **Add a table → Import data → CSV file**, choose `Employees & Positions.csv`,
   name the table **`Employees & Positions`**.
2. Set the primary field to **`Position ID`**.
3. Convert these fields after import:

   | Field | Type | Notes |
   | --- | --- | --- |
   | `Future Manager` | **Link to Employees & Positions** | self-link, matched on `Position ID` |
   | `[F] Supervisory Organization 🔗` | **Link to Supervisory Organizations** | matched on the org's primary field |
   | `[D] Employee Decision` | Single select | `Retain`, `Transfer`, `Redeploy`, `Exit`, `To be confirmed` |
   | `Future Organization`, `[E] Location`, `[E] Job Family`, `[E] Grade`, `[E] Employment Type`, `[E] Position Status` | Single select | |
   | `[E] Email` | Email | |
   | `[E] FTE` | Number (1 decimal) | |
   | `[E] Start Date` | Date | ISO `YYYY-MM-DD` |

   Keep `[E] Employee ID` and `[F] Manager ID` as **plain text** — the chart
   builds the hierarchy from this id pair first and only falls back to the
   link field, which is what makes it robust when two people share a name.

The emoji in `[F] Supervisory Organization 🔗` is deliberate: it mirrors the
production field name and exercises the extension's tolerant field resolution.
If your import drops it, the field still resolves.

### 3. Org Design Data

1. **Add a table → Import data → CSV file**, choose `Org Design Data.csv`,
   name the table **`Org Design Data`**.
2. Leave the primary field as **`Slide Title`**.
3. Convert after import:

   | Field | Type | Notes |
   | --- | --- | --- |
   | `Current HC`, `Future HC` | Number (integer) | |
   | `FTE` | Number (1 decimal) | |
   | `Stack` | Single select | `Current`, `Future` — **blank is meaningful**: the row counts on both sides |
   | `Status` | Single select | `Mapped`, `In selection process`, `Posted`, `At risk` |
   | `Level`, `Section Level` | Single select | `DLT`, `DLT-1`, `DLT-2`, `DLT-3` |
   | `Slide Title`, `Section Name`, `Supervisory Organization`, `DLT`…`DLT-6` | Single line text | |

   No link fields — this table is deliberately flat. `DLT`…`DLT-6` describe the
   **slide's** place in the ladder (blank below its own level), which is what the
   hierarchical filter nests on; they are not the row's own lineage.

### 4. Org Design Notes

1. **Add a table → Import data → CSV file**, choose `Org Design Notes.csv`,
   name it **`Org Design Notes`**, primary field **`Slide`**.
2. Set `Potential People Impact` and `Organizational Ambition` to **Long text** —
   each line becomes a bullet in the notes band.

The `Slide` values must match `Slide Title` in the data table exactly; matching
is case- and whitespace-insensitive, but nothing else.

### 5. Programme Milestones

1. **Add a table → Import data → CSV file**, name it **`Programme Milestones`**,
   primary field **`Milestone ID`**.
2. Convert after import:

   | Field | Type | Notes |
   | --- | --- | --- |
   | `Due Date` | Date | ISO `YYYY-MM-DD` |
   | `Status` | Single select | `Complete`, `In progress`, `Not started`, `Blocked` |
   | `RAG` | Single select | `Green`, `Amber`, `Red` |
   | `Phase` | Single select | `Design`, `Consultation`, `Selection`, `Transition`, `Close` |
   | `Progress` | Number (integer, 0–100) | |

   Dates are anchored to **9 September 2026** (the `BASELINE` constant in
   `generate.py`). Move it forward when the demo starts to look stale — the
   whole plan shifts with it, keeping "past due" and "next 14 days" meaningful.

### 6. Employee Conversations

1. **Add a table → Import data → CSV file**, name it **`Employee Conversations`**,
   primary field **`Conversation ID`**.
2. Convert after import:

   | Field | Type | Notes |
   | --- | --- | --- |
   | `Status` | Single select | `Held`, `Scheduled`, `To schedule`, `Declined` |
   | `Conversation Type` | Single select | |
   | `Sentiment` | Single select | `Positive`, `Neutral`, `Concerned`, `Distressed` |
   | `Scheduled Date`, `Held Date` | Date | |

   Every row is a person the scenario marks at risk or in selection, so this
   table reconciles with `Org Design Data`. The view compares the two and shows
   an **Untracked** count when the design owes more conversations than the
   tracker holds.

## What the data is built to exercise

- **Vacant positions** — 9 rows have no `[E] First Name, Last Name`. One of
  them (`Analytics Manager`, org `DSGAI`) is a **manager** with reports, which
  is the case that renders as "Role title (Vacant)" rather than a person.
- **Hierarchical short codes** — `DSG` → `DSGA` → `DSGAE`. A leader scoped to
  `DSG` sees exactly the rows whose `Short Code` starts with `DSG`, which is
  how the per-leader scoping in `config.js` works.
- **Every SO Status and Scoping value**, so both legends on the stacked chart
  are fully populated (including one `Decommissioned SO`).
- **Uneven spans of control** — from 2 to 10 direct reports, so the dashboard's
  span-of-control buckets and the "managers with ≤2 reports" tile are non-trivial.
- **Part-time FTE** — roughly 1 in 8 filled positions is below 1.0, so headcount
  and FTE differ.

And in the deck data specifically:

- **All four status buckets are populated**, so every KPI column and every slot
  colour is exercised: 20 at-risk headcount, 43 posted, 20 in selection.
- **Both sides are non-empty on every slide**, so no page renders half-blank.
- **Blank `Stack` rows** (unchanged positions) alongside explicit `Current` and
  `Future` rows — the three cases the model has to handle differently.
- **Slides that need more than one page**, so pagination and the `(1/2)` page
  labels are exercised rather than dead code.
- A **vacant manager** carried through as a posted role on the future side.

The restructuring scenario itself lives in `SCENARIO` at the top of
`generate.py` — one entry per supervisory org, naming the roles that are new,
at risk, or in a selection process. Edit it to model a different change; the
deck follows.

## Regenerating

```bash
python3 generate.py     # deterministic: same seed, same data
```

Edit `ORG_TREE` at the top of the script to change the shape of the
organisation; everything else (people, IDs, rollups) follows from it.

## Verifying

From the extension root, `npm run check:data` runs all three models over these
CSVs without Airtable and asserts every consistency claim above — including that
the deck's current headcount matches the filled positions in the people table,
that pagination covers every org exactly once, and that the KPI columns
reconcile with their status buckets.
