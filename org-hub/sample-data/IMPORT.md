# Sample data — import guide

Two CSVs that together describe one fictional 150-position organisation
(**Aurora Health Group**, 24 supervisory organisations, 4 management layers,
9 vacant positions). They are generated by `generate.py` and are internally
consistent: every manager reference resolves, every person sits in a
supervisory org that exists, and each org's headcount rollup equals the FTE of
its direct members.

| File | Rows | Becomes |
| --- | --- | --- |
| `Employees & Positions.csv` | 150 | the people table — one row per **position**, filled or vacant |
| `Supervisory Organizations.csv` | 24 | the supervisory-org table — one row per org unit |

Nothing here is real. Names, emails (`@aurorahealth.example`) and IDs are
synthetic.

## Import order

Import **Supervisory Organizations first**, then Employees & Positions — the
people table links into it.

### 1. Supervisory Organizations

1. In your base: **Add a table → Import data → CSV file**, choose
   `Supervisory Organizations.csv`, name the table **`Supervisory Organizations`**.
2. Set the primary field to **`Supervisory Organization`**.
3. Convert these fields after import:

   | Field | Type | Notes |
   | --- | --- | --- |
   | `Parent Supervisory Organization` | **Link to Supervisory Organizations** | self-link; Airtable matches on the primary field |
   | `SO Status` | Single select | `No Changes SO`, `New SO - Draft`, `New SO`, `Updated SO`, `Decommissioned SO` |
   | `Scoping` | Single select | `In Scope`, `Out of Scope` |
   | `Org Level` | Number (integer) | |
   | `[C] SupOrgAssignement % Rollup (from Employees & Positions / FUTURE)` | Number (1 decimal) | in the real base this is a rollup; here it is a plain number |

   The root row (`Executive Office …`) has an empty parent — that's correct,
   it is the top of the tree.

### 2. Employees & Positions

1. **Add a table → Import data → CSV file**, choose `Employees & Positions.csv`,
   name the table **`Employees & Positions`**.
2. Set the primary field to **`Position ID`**.
3. Convert these fields after import:

   | Field | Type | Notes |
   | --- | --- | --- |
   | `Future Manager` | **Link to Employees & Positions** | self-link, matched on `Position ID` |
   | `[F] Supervisory Organization 🔗` | **Link to Supervisory Organizations** | matched on the org's primary field |
   | `[D] Employee Decision` | Single select | `Retain`, `Transfer`, `Redeploy`, `Exit`, `To be confirmed` |
   | `Future Organization`, `[E] Location`, `[E] Job Family`, `[E] Grade`, `[E] Employment Type`, `[E] Position Status` | Single select | |
   | `[E] Email` | Email | |
   | `[E] FTE` | Number (1 decimal) | |
   | `[E] Start Date` | Date | ISO `YYYY-MM-DD` |

   Keep `[E] Employee ID` and `[F] Manager ID` as **plain text** — the chart
   builds the hierarchy from this id pair first and only falls back to the
   link field, which is what makes it robust when two people share a name.

The emoji in `[F] Supervisory Organization 🔗` is deliberate: it mirrors the
production field name and exercises the extension's tolerant field resolution.
If your import drops it, the field still resolves.

## What the data is built to exercise

- **Vacant positions** — 9 rows have no `[E] First Name, Last Name`. One of
  them (`Analytics Manager`, org `DSGAI`) is a **manager** with reports, which
  is the case that renders as "Role title (Vacant)" rather than a person.
- **Hierarchical short codes** — `DSG` → `DSGA` → `DSGAE`. A leader scoped to
  `DSG` sees exactly the rows whose `Short Code` starts with `DSG`, which is
  how the per-leader scoping in `config.js` works.
- **Every SO Status and Scoping value**, so both legends on the stacked chart
  are fully populated (including one `Decommissioned SO`).
- **Uneven spans of control** — from 2 to 10 direct reports, so the dashboard's
  span-of-control buckets and the "managers with ≤2 reports" tile are non-trivial.
- **Part-time FTE** — roughly 1 in 8 filled positions is below 1.0, so headcount
  and FTE differ.

## Regenerating

```bash
python3 generate.py     # deterministic: same seed, same data
```

Edit `ORG_TREE` at the top of the script to change the shape of the
organisation; everything else (people, IDs, rollups) follows from it.

## Verifying

From the extension root, `npm run check:data` runs the two org models over
these CSVs without Airtable and asserts the consistency claims above.
